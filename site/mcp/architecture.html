Kvit MCP · opbygning

En tynd klient, med vilje

MCP-serveren oversætter værktøjskald fra en AI-assistent til HTTP-kald mod Kvits eget JSON-API. Den har ingen regler selv. Nummerserien, uforanderligheden og revisionssporet håndhæves ét sted, i programmet, og serveren får præcis de samme svar og afslag som browseren. Hele koden kan man læse på en eftermiddag.

Afhængigheder

To pakker i produktion: MCP-SDK'et og Zod til skemaerne. Ingen HTTP-ramme, ingen database-driver, ingen ORM; Node's egen fetch og node:http er nok.

  • @modelcontextprotocol/sdk
  • zod

Til udvikling desuden @types/node, tsx, typescript, vitest.

Reglerne, den er bygget efter

Den åbner aldrig databasen

Serveren kender ikke filstien, har ingen driver og ingen ORM. Det er en test, ikke en hensigt: test/04-static.test.ts søger hele mcp/ igennem for database-drivere, ORM-imports og database-stier og fejler, hvis nogen af dem dukker op. Samme test tjekker, at klienten kun kender GET og POST, så der findes ingen vej til at slette eller redigere noget.

Alle regler bor i programmet

Vil assistenten sætte betalingsdato på en faktura, der er krediteret, svarer programmet 409 med sin egen danske besked, og serveren sender den videre uændret med retry: false og en opfordring til at sige det til ejeren. Der er ingen anden kopi af reglerne at holde i sync.

Kun tilføjelser

Skriveværktøjerne tilføjer en række (bankbevægelse, udgift, kladde, time) eller sætter en dato (betalt). Ingen af dem udsteder, krediterer, sletter eller retter noget, der findes. Hver skrivning får actor = "api" i revisionssporet, så man i eksporten kan se, hvad der kom fra AI'en.

Tokenet bliver på serversiden

Over HTTP-transporten sender klienten intet token; det ligger i serverens miljø og følger med hvert kald til programmet. Over stdio kører serveren som en proces hos klienten og får tokenet i sin env-blok. Rækkefølgen, når serveren leder efter det: shellen, så mcp/.env, så programmets egen .env, hvor API_TOKEN genbruges, så ét token kan ligge ét sted.

HTTP-transporten er stateless og uden eget login

Hvert kald får sin egen server og transport, og der er ingen session at kapre. Til gengæld har endpointet ikke noget login: den, der kan nå porten, kan bruge værktøjerne. Derfor binder den til 127.0.0.1, og over VPN binder man til tailnet-adressen og ikke mere. Host-headeren valideres (beskyttelse mod DNS-rebinding), så en webside, der peger et offentligt navn mod din maskine, ikke kan kalde skriveværktøjerne fra din browser.

Testene

Testene snyder ikke med en mock. De bygger programmet, starter det mod en frisk database med demodata og et API_TOKEN, kobler en rigtig MCP-klient på serveren over en in-memory-transport og kører hvert værktøj gennem protokollen:

  • værktøjslisten og skemaerne er dem, siden Værktøjer viser,
  • hvert læseværktøj mod håndregnede tal fra demodataene, i øre,
  • hvert skriveværktøj mod programmets API bagefter, inklusive revisionsrækken med actor = api,
  • afstemningen bogfører præcis differencen, og ved næste kald ingenting,
  • forkert og manglende token får alle værktøjer til at fejle uden at ændre noget,
  • og den statiske søgning efter databaseadgang beskrevet ovenfor.
npm run build        # programmet, én gang
npm run mcp:test     # bygger og tester serveren mod det

Kør den selv

npm run mcp                  # stdio, fra kildekode (tsx)
npm run mcp:http             # streamable HTTP på http://127.0.0.1:3333/mcp
npm --prefix mcp run inspect # MCP Inspector mod den byggede server
npm --prefix mcp run docs    # genererer disse sider fra serveren

Miljøvariabler, .env-filer og transportdetaljer står i mcp/README.md (engelsk). I Docker-installationen og den selvstændige version er serveren bygget med og startes automatisk; se Tilslut.

Kvit · MCP-serveren er en del af kildekoden og udgives sammen med programmet.
